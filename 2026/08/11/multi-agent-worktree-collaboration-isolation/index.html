1. 前置条件与 Worktree 槽位 Agent 选型技术规范

将 AI Agent 工具引入 Git Worktree 独立槽位之前，必须从技术可行性角度审查其是否具备充当物理隔离工位的能力。

1.1 核心选型四大硬性标准 (Crucial Requirements)

能够充当独立 Worktree 工位的 Agent 必须同时满足以下四大硬性标准：

  1. 具备完整 Code CLI / 命令行交互控制能力：
    • 能够单独在指定 Worktree 路径下启动 CLI 进程，具备自主读取文件、修改代码、执行终端命令及管理 Session 上下文的全套能力。
  2. 支持免鉴权 / 无痛跳过 Web 登录：
    • 允许通过本地配置文件（如 .claude/settings.*.json、.opencode/opencode.jsonc）、环境变量或 API Token 直接启动，无需依赖浏览器 OAuth 交互或手动点击登录。
  3. 支持自定义 API 端点与订阅 (Custom Endpoint & Subscription)：
    • 允许开发者灵活配置 BaseURL、自定义 API Key 或映射企业内部/个人第三方订阅（如 Ark、GLM、Claude/OpenAI 兼容端点），不强制绑定单一商业平台账号。
  4. API 接口兼容范围（决定性标准）：
    • 仅”提供 base_url 配置项”并不等于可接第三方端点——真正决定能否接入第三方端点的，是 CLI 的 Provider 层是否同时兼容 Anthropic Messages 与 OpenAI Chat Completions 两种 API 接口规范。槽位 Agent 的 Provider 层必须同时兼容这两种 API 规范，否则会陷入”看似支持自定义端点、实则 API 规范锁死”的陷阱（典型反例：Codex CLI，详见 1.2）。判定根因矩阵见 1.2.1。

1.2 主流 Agent 工具 Worktree 槽位适配分析

针对当前常见 Agent 工具在 CLI 完整性、免鉴权、自定义端点与 API 兼容范围上的表现（基于 2026-08 官方文档与源码核实），结论如下：

🟡 条件适配（视 API 兼容范围与实测） Aider、Copilot CLI、Trae agent、CodeBuddy、Kilo Code

1.2.1 判定根因：API 接口兼容范围决定端点接入能力

四大硬性标准中，第三条”自定义端点”的颗粒度决定胜负。能否接入第三方端点，本质取决于 CLI 的 Provider 层是否同时兼容 Anthropic Messages 与 OpenAI Chat Completions 两种 API 规范，而非”是否提供 base_url 配置项”。Codex CLI 是典型反例——它支持自定义 base_url，却因 Provider 层仅实现 Responses API 而无法接入任何主流第三方端点。

选型铁律：只有”双协议兼容”类 CLI 才是真正灵活的常驻槽位。评估任何新 CLI 时，先查其 Provider 层是否同时兼容 Anthropic Messages 与 OpenAI Chat Completions 两种 API 规范，否则会重蹈 Codex”看似支持自定义端点、实则 API 规范锁死”的误判。

2. 概述与核心理念

2.1 基本工作环境：一个主 GUI Agent + 多个 CLI Agent

本教程的工作环境是双层结构：

  • 主 GUI Agent（1 个，主控）：在仓库主工作区（master 分支）运行的图形化 IDE 型 Agent（如 Trae / Antigravity / Cursor 等）。负责架构规划、全局可视化、任务调度、最终合并审查与统一 git push，不直接参与并发细节编写。
  • CLI Agent（N 个，并发）：在各自的 Git Worktree 目录中启动的命令行 Agent（如 Claude Code / OpenCode，完整选型见 1.2）。每个 CLI Agent 独占一个 Worktree 槽位与分支，并发执行具体任务，各自本地 commit，严禁 push。

操作模式：你坐在主 GUI Agent 前做主控与调度；同时打开多个终端，各自进入不同 Worktree 目录，启动不同 CLI Agent 并发干活。主工作区与各 Worktree 共享同一个底层 .git 仓库（分支、历史、Tag 全局打通），但工作区目录物理隔离、互不干扰。

2.2 为什么需要 Worktree 物理隔离

传统单工作区分支切换在多 Agent 并发下有三个致命痛点：

  1. 工作区冲突：不同 Agent 会互相覆盖未提交的本地修改或锁死文件。
  2. 上下文污染：不同 Agent 共享同一个会话上下文，导致提示词与上下文粘连。
  3. 配置与技能互斥：不同 Agent 调用的模型（Model）、MCP 服务、Skill 体系及 API 端点存在差异，无法共用一套配置文件。

为此，采用 Git Worktree + 常驻槽位分支 + 自动化基线同步 架构：主 GUI Agent 守在 master，每个 CLI Agent 占一个常驻 Worktree 槽位独立干活，完成后由主工作区统一合并与基线同步。

本质研判：Worktree 隔离了什么，没隔离什么？

  • Worktree 隔离了：终端运行态、编译缓存、未提交脏代码（Uncommitted Changes）与槽位私有配置（.claude/ / .opencode/）。
  • Worktree 并没有隔离：相同文件的文本修改冲突。若不同 Agent 修改不同文件，Git 会自动并入（Auto-merge），甚至无需 Worktree 亦可顺利合并；若不同 Agent 修改同一文件，Worktree 只是把文本冲突推迟到了在 master 执行 git merge 的那一刻。因此，冲突的最终解决依赖于主工作区的无损合并机制（见 6.2 节）。

6. 什么时候不能使用脚本同步？（边界与避坑）

在以下 4 种场景下必须禁止使用脚本，改用手动干预：

❌ 场景 1：任何槽位存在未提交的修改 (Uncommitted Changes / Dirty Tree)

  • 原因：git rebase master 要求工作树必须干净。如果某个 Agent 正在写代码且未 commit，反向 Rebase 会触发失败或把脏代码混入冲突。
  • 处置：先让 Agent 完成 commit 或使用 git stash 暂存后再同步。

❌ 场景 2：存在代码/文档冲突 (Merge / Rebase Conflict)

  • 原因：当多个 Agent 修改了同一文件的同一位置，worktree-sync.js 脚本会在 git merge 时检测到冲突并自动安全中断退出（报 ❌ 分支 [...] 合并存在冲突）。
  • 处置与无损叠加 SOP：
    1. 阻断停手：脚本中断后，子槽位 Agent 无需作任何修改，保留自身 commit 即可。
    2. 主工作区解决：主 Agent（或用户）在 master 主工作区打开冲突文件。
    3. 硬约束：无损叠加（A + B）原则：严禁偷懒使用 git checkout --ours/theirs 或直接覆盖某一方内容！合并时必须同时保留 Agent A 与 Agent B 的有效代码/ Markdown 章节，采用追加或结构化拼接的方式融合两者的修改。
    4. 验证与恢复：完成冲突解决后，运行构建/测试命令校验（如 pnpm build），确认无语法破坏后执行 git commit，随后重新运行 pnpm worktree:sync 完成推送与基线同步。

❌ 场景 3：大版本重构或破坏性目录调整 (Massive Refactoring)

  • 原因：当涉及跨目录搬迁或批量重命名文件时，自动 Rebase 极易产生复杂冲突。
  • 处置：先在 master 完成重构并提交，随后手动进入各个子 Worktree 执行 git rebase master。

❌ 场景 4：交互式/需要手工确认的 Git 状态

  • 原因：脚本是以非交互模式运行的，无法处理 GPG 签名弹窗或 SSH 口令输入。

7. 最佳实践与协作纪律总结 (Four Golden Rules)

多 Agent 并发协作必须严格遵守以下四条高压红线纪律（写进 AGENTS.md 强制生效）：

  1. 文件修改隔离与追加律：不同 Agent 尽可能修改不同文件；若必须修改同一文件，采用追加（Append）或定位精确修改，严禁重写/清空已有文本。
  2. 外科手术式提交律：只 git add <本任务具体文件>，严禁 git add . / commit -a；提交前校验改动范围，防止污染其他 Agent 代码。
  3. 常驻槽位物理禁 push 律：子槽位（project-claude / project-opencode 等）只做本地 commit，物理禁 push 且禁删 Worktree/分支。git push 统一由主工作区（master）在完成合并后执行。
  4. 主工作区无损合并律（A + B）：合并冲突由主仓库 worktree:sync 捕获，主 Agent 在 master 解决冲突时必须遵循”无损叠加（A + B）”原则，严禁覆盖或剔除另一方的有效改动，且合并后须通过构建校验。

踩坑三条：

  1. models.yml 勿写字面 key——该文件易分享/入库。统一 apiKey: <ENV_VAR_NAME> 引用，key 放 ~/.omp/agent/.env（权限 600）。
  2. .omp/ 必须进 .gitignore——含 skills 符号链接与（若有）项目级 .env，属 Agent 私有，类比 .trae / .claude/skills。
  3. provider 仅全局，无项目级隔离——不像 CC 能按项目隔离 provider；多端点切换靠 --model provider/model flag 或多 profile（omp --profile）。

B.4 架构演进：统一算力池网关 → 全局统一端点

  • 现状（个人套餐直连）：各 Agent 走各自 key，端点配置散落项目级/全局，TPM/RPM 受个人套餐钳制。
  • 目标（统一网关建成）：自建统一算力池网关后，所有 Agent 指向同一内部端点（一份全局 provider 配置），配额由网关统一调度、高低负载均衡。
  • 趋势：生产级网关一旦建立，全部 Agent 收敛为「全局端点配置」单一范式——本附录的全局 models.yml 即该终态预演；个人直连期的项目级隔离配置随网关落地逐步退役。
