1. Prerequisites and Worktree Slot Agent Selection Criteria

To introduce an AI Agent tool into an isolated Git Worktree slot, you must first evaluate whether it is technically capable of serving as a physically isolated workstation.

1.1 Four Hard Requirements for Slot Eligibility

An Agent qualified to occupy an independent Worktree slot must satisfy all four of the following criteria simultaneously:

  1. Full Code CLI / command-line interaction capability:
    • Must be able to launch a CLI process at a designated Worktree path, with the full ability to autonomously read files, modify code, execute terminal commands, and manage session context.
  2. Authentication-free / seamless skip of web login:
    • Must support direct launch via local configuration files (e.g., .claude/settings.*.json, .opencode/opencode.jsonc), environment variables, or API tokens, without requiring browser-based OAuth interaction or manual login clicks.
  3. Custom API endpoint and subscription support:
    • Must allow developers to flexibly configure BaseURL, custom API keys, or map to enterprise/personal third-party subscriptions (e.g., Ark, GLM, Claude/OpenAI-compatible endpoints), without being locked into a single commercial platform account.
  4. API compatibility range (the decisive criterion):
    • Merely “exposing a base_url configuration field” does not equal true third-party endpoint compatibility — what actually determines whether third-party endpoints can be connected is whether the CLI’s Provider layer is compatible with both the Anthropic Messages and OpenAI Chat Completions API specifications. The slot Agent’s Provider layer must be compatible with both API specifications simultaneously; otherwise, you fall into the trap of “appearing to support custom endpoints while being API-spec-locked” (canonical counterexample: Codex CLI, see 1.2). See the root-cause matrix in 1.2.1.

1.2 Mainstream Agent Tool Worktree Slot Compatibility Analysis

Based on CLI completeness, authentication-free operation, custom endpoint support, and API compatibility range (verified against official documentation and source code as of 2026-08), the verdict is as follows:

Tier Tools
🟢 Fully Compatible (Recommended for Worktree slots) Claude Code, OpenCode, Crush, Qwen Code, oh-my-pi
🟡 Conditionally Compatible (Depends on API compatibility range and testing) Aider, Copilot CLI, Trae agent, CodeBuddy, Kilo Code
🔴 Not Compatible (API-spec-locked or account-bound) Codex, Gemini, Cursor/Amp, ZCode, iFlow, Comate, CodeGeeX/Doubao MarsCode/iFlyCode, Antigravity CLI (agy), Continue, Antigravity/Trae/Cursor/Windsurf and other GUI-IDE-type agents

1.2.1 Root Cause: API Compatibility Range Determines Endpoint Access

Among the four hard requirements, the granularity of criterion #3 — “custom endpoints” — is the deciding factor. Whether third-party endpoints can be connected fundamentally depends on whether the CLI’s Provider layer is compatible with both the Anthropic Messages and OpenAI Chat Completions API specifications, not on whether a base_url configuration field exists. Codex CLI is the canonical counterexample: it supports custom base_url, yet its Provider layer only implements the Responses API, making it incompatible with virtually all mainstream third-party endpoints.

Provider Compatibility Range Representative CLI Compatible Endpoints
Dual-Spec Compatible Claude Code / OpenCode / Crush / Qwen Code / Kilo Code Ark Anthropic endpoint + GLM OpenAI endpoint, both sides ✅
OpenAI Chat Completions Aider / GitHub Copilot CLI OpenAI-compatible endpoints only (GLM ✅; Ark requires OpenAI-compatible mode)
OpenAI Responses API Codex CLI No mainstream third-party endpoint implements this API ❌
Gemini proprietary Gemini CLI Google-only ❌

Selection Iron Law: Only “dual-spec compatible” CLI tools qualify as truly flexible persistent slots. When evaluating any new CLI, first check whether its Provider layer is compatible with both the Anthropic Messages and OpenAI Chat Completions API specifications — otherwise, you will repeat the Codex misjudgment of “appearing to support custom endpoints while being API-spec-locked.”

2. Overview and Core Concepts

2.1 Basic Work Environment: One Main GUI Agent + Multiple CLI Agents

The work environment described in this tutorial follows a two-tier architecture:

  • Main GUI Agent (1 instance, orchestrator): A graphical IDE-type Agent (e.g., Trae / Antigravity / Cursor) running in the repository’s main workspace (master branch). Responsible for architecture planning, global visualization, task scheduling, final merge review, and unified git push. It does not directly participate in concurrent detail-level coding.
  • CLI Agents (N instances, concurrent): Command-line Agents (e.g., Claude Code / OpenCode; see 1.2 for the full selection) launched in their respective Git Worktree directories. Each CLI Agent exclusively occupies one Worktree slot and branch, executes specific tasks concurrently, performs local commit, and is strictly forbidden from push.

Operating Model: You sit in front of the main GUI Agent as the orchestrator and scheduler; simultaneously, you open multiple terminals, each entering a different Worktree directory, and launch different CLI Agents to work concurrently. The main workspace and all Worktrees share the same underlying .git repository (branches, history, and tags are globally connected), but the working directories are physically isolated and do not interfere with each other.

2.2 Why Physical Worktree Isolation Is Necessary

Traditional single-workspace branch switching suffers from three fatal pain points under multi-agent concurrency:

  1. Workspace conflicts: Different Agents overwrite each other’s uncommitted local changes or lock files.
  2. Context pollution: Different Agents share the same session context, leading to prompt and context entanglement.
  3. Configuration and skill mutual exclusion: Different Agents invoke different models, MCP services, skill systems, and API endpoints, making it impossible to share a single set of configuration files.

The solution is the Git Worktree + Persistent Slot Branch + Automated Baseline Synchronization architecture: the main GUI Agent guards master, while each CLI Agent occupies a persistent Worktree slot to work independently. Upon completion, the main workspace performs unified merge and baseline synchronization.

Fundamental Assessment: What Worktree Does and Does Not Isolate

  • Worktree isolates: terminal runtime state, build caches, uncommitted dirty code, and slot-private configuration (.claude/ / .opencode/).
  • Worktree does NOT isolate: textual merge conflicts on the same file. If different Agents modify different files, Git auto-merges seamlessly — Worktree isn’t even strictly necessary. If different Agents modify the same file, Worktree merely defers the textual conflict to the moment git merge is executed on master. The ultimate resolution of conflicts therefore depends on the main workspace’s lossless merge mechanism (see Section 6.2).

4.2 Model and Custom Subscription/Endpoint Isolation SOP

For custom subscription configuration targeting Anthropic-compatible endpoints, the baseURL concatenation logic differs critically across CLI tools (must be strictly followed to avoid 404 errors):

  • OpenCode CLI (.opencode/opencode.jsonc):
    • Underlying SDK is @ai-sdk/anthropic, which automatically appends /messages to the baseURL.
    • baseURL must end with /v1 (e.g., https://ark.cn-beijing.volces.com/api/coding/v1 or https://.../api/anthropic/v1).
  • Claude Code CLI (.claude/settings.*.json):
    • Underlying SDK automatically appends /v1/messages to the baseURL.
    • ANTHROPIC_BASE_URL must NOT include /v1 (e.g., https://ark.cn-beijing.volces.com/api/coding).

6. When NOT to Use Script Sync (Boundaries and Pitfalls)

In the following 4 scenarios, script usage must be forbidden in favor of manual intervention:

❌ Scenario 1: Any Slot Has Uncommitted Changes (Dirty Tree)

  • Why: git rebase master requires a clean working tree. If an Agent is actively writing code without committing, the reverse rebase will either fail or mix dirty code into conflicts.
  • Action: First have the Agent complete its commit, or use git stash to temporarily shelve changes before syncing.

❌ Scenario 2: Code/Document Merge Conflicts (Merge / Rebase Conflict)

  • Why: When multiple Agents modify the same location in the same file, the worktree-sync.js script detects the conflict during git merge and safely aborts (reporting ❌ Branch [...] merge conflict detected).
  • Action and Lossless Superposition SOP:
    1. Stop immediately: After the script aborts, child slot Agents should make no changes — keep their commits as-is.
    2. Resolve in main workspace: The main Agent (or the user) opens the conflicting files in the master main workspace.
    3. Hard constraint: Lossless Superposition (A + B) Principle: Never take the lazy route of git checkout --ours/theirs or directly overwrite one side’s content! When merging, you must simultaneously preserve the valid code / Markdown sections from both Agent A and Agent B, using append or structured concatenation to fuse both modifications.
    4. Verify and recover: After resolving conflicts, run build/test commands (e.g., pnpm build) to verify no syntax breakage, then execute git commit, and re-run pnpm worktree:sync to complete the push and baseline sync.

❌ Scenario 3: Massive Refactoring or Destructive Directory Restructuring

  • Why: Cross-directory moves or batch file renames easily produce complex conflicts during automatic rebase.
  • Action: First complete the refactoring on master and commit, then manually enter each child Worktree and execute git rebase master.

❌ Scenario 4: Interactive Git States Requiring Manual Confirmation

  • Why: The script runs in non-interactive mode and cannot handle GPG signature prompts or SSH passphrase input.

7. Best Practices and Collaboration Discipline Summary (Four Golden Rules)

Multi-agent concurrent collaboration must strictly adhere to the following four non-negotiable red-line rules (encoded in AGENTS.md for mandatory enforcement):

  1. File Modification Isolation and Append Rule: Different Agents should modify different files whenever possible; if the same file must be modified, use append or precise targeted edits, and strictly forbid rewriting or clearing existing text.
  2. Surgical Commit Rule: Only git add <specific files for this task>, strictly forbid git add . / commit -a; verify the scope of changes before committing to prevent contaminating other Agents’ code.
  3. Persistent Slot Physical No-Push Rule: Child slots (project-claude / project-opencode, etc.) only perform local commits; physically forbid push and forbid deletion of Worktree/branch. git push is exclusively executed by the main workspace (master) after merge completion.
  4. Main Workspace Lossless Merge Rule (A + B): Merge conflicts are caught by the main repository’s worktree:sync; when resolving conflicts on master, the orchestrating Agent must follow the “Lossless Superposition (A + B)” principle, strictly forbidding overwriting or discarding either side’s valid changes, and must pass build verification after merging.

B.1 Prerequisite Awareness: The Compute Pool Is the Real Bottleneck for Concurrency

The hard bottleneck for multi-agent concurrency is not Worktree (the Git layer is nearly unlimited), but rather the TPM/RPM quotas of each AI coding subscription. Personal coding plan concurrency limits are generally low — running several slots simultaneously will quickly hit rate limits. Three approaches, in increasing ROI:

Path Description Suitable For
Direct personal subscription Each Agent uses its own key/subscription, project-level isolation Early stage, small teams, low concurrency
Unified compute pool gateway Self-built gateway aggregating multiple compute sources, load balancing across high/low tiers, unified internal quota distribution Team/enterprise, high concurrency
DeepSeek API direct Extremely cost-effective direct connection, practically sufficient Individual/small team fallback

B.3 Key Differences and Pitfalls (oh-my-pi vs Claude Code / OpenCode)

Dimension Claude Code OpenCode oh-my-pi
Endpoint config granularity Project-level .claude/settings.local.json + global Project-level opencode.json + global Custom provider global only ~/.omp/agent/models.yml
Key storage env / settings config / env env reference + ~/.omp/agent/.env
baseURL convention Without /v1 With /v1 As-is per models.yml baseUrl (api field determines path concatenation)

Three pitfalls:

  1. Never inline literal keys in models.yml — this file is easily shared/committed. Always use apiKey: <ENV_VAR_NAME> references, with the actual key in ~/.omp/agent/.env (permissions 600).
  2. .omp/ must be in .gitignore — contains skills symlinks and (if present) project-level .env; it is Agent-private, analogous to .trae / .claude/skills.
  3. Provider is global only, no project-level isolation — unlike CC, which can isolate providers per project; multi-endpoint switching relies on the --model provider/model flag or multiple profiles (omp --profile).

B.4 Architecture Evolution: Unified Compute Pool Gateway → Global Unified Endpoint

  • Current state (direct personal subscription): Each Agent uses its own key, endpoint configurations are scattered across project-level and global, TPM/RPM constrained by personal plan limits.
  • Target state (once the unified gateway is built): After deploying a self-built unified compute pool gateway, all Agents point to the same internal endpoint (a single global provider configuration), with quotas uniformly scheduled and load-balanced by the gateway.
  • The trend: Once a production-grade gateway is established, all Agents converge to the single paradigm of “global endpoint configuration” — the global models.yml in this appendix is a preview of that end state; project-level isolation configurations from the direct-subscription era will be gradually retired as the gateway rolls out.
