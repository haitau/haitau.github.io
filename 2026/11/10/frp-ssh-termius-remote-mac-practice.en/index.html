Remote Access to a Private Mac: Full-Stack Guide with frp, SSH, and Termius

Production Baseline: macOS (Apple Silicon) + frp 0.72.0 + Cloud Linux VPS (Debian 12) + Termius (iOS / Android) + herdr persistent session layer.

1. The Problem: You Are Away, Your Mac Is Behind NAT

Your Mac is running workloads you cannot afford to abandon—a long compilation job, local microservices, a dozen concurrent AI coding agent sessions, or a carefully arranged terminal workspace. When you step away from your desk, you have only two choices: head back, or connect remotely.

Most developers instinctively reach for remote desktop tools (RustDesk, TeamViewer, AnyDesk) to stream the Mac screen to their phone. It works in theory, but the mobile experience is miserable: driving a 27-inch desktop on a 6-inch touchscreen means drifting cursors, illegible text, and full-screen TUI redraws that smear into compression artifacts. What you actually need to control is not “the Mac’s screen”—it is those specific terminal sessions. And the native protocol for terminal sessions is SSH.

The obstacle is network topology: a Mac at home or in the office sits behind NAT without a public IPv4 address. How does your phone reach it? This guide walks through a battle-tested setup using a minimal cloud VPS + frp to bridge the NAT gap, paired with Termius and the herdr persistent session layer to connect from anywhere in the world directly into your Mac shell—covering architecture trade-offs, deployment, sshd hardening, push notifications, and three hard-won troubleshooting traps.

2. Architecture Trade-Offs: Why frp + SSH?

Before building this pipeline, I evaluated every viable remote takeover route as of November 2026:

Three decisive engineering reasons make frp + SSH + Persistent Session Layer the clear winner:

  1. Universal takeover of already-running sessions. By running a persistent session layer on the Mac (this guide uses herdr, a terminal multiplexer purpose-built for AI coding agents), a background daemon owns every pseudo-terminal (PTY). No matter how many times SSH disconnects, the processes stay alive in place, and re-attaching restores the exact state instantly. Unlike Happy or Paseo—which can only manage sessions they spawn from scratch—this approach works for everything already running on your machine.
  2. Complete endpoint decoupling. Many engineering teams route Claude Code or OpenCode through enterprise LLM gateways or Anthropic-compatible endpoints (such as GLM or Volcengine Ark). Claude’s official Remote Control strictly requires direct authentication against api.anthropic.com with no custom ANTHROPIC_* environment overrides. Because an SSH tunnel operates purely at the transport layer, it is 100% agnostic to which model endpoint your agents use.
  3. Zero marginal cost with an existing VPS. frp is a battle-tested reverse proxy for NAT traversal (80k+ GitHub stars) that runs in a few megabytes of RAM on any entry-level cloud instance.

3. System Architecture: Three Orthogonal Planes

The system is intentionally decoupled into three orthogonal planes, each solving exactly one problem:

  • 1. Tunnel Plane (frp) — Reachability: Because the Mac sits behind NAT without a public IP, frpc on the Mac initiates an outbound persistent connection to frps :7000 on the cloud VPS. Connecting via SSH from your phone to VPS port :6022 transparently forwards traffic to 127.0.0.1:22 on the Mac.
  • 2. Session Plane (herdr) — Continuity: A background server daemon holds the PTY file descriptors for all panes. Whether your phone drops signal in an elevator, switches between Wi-Fi and cellular, or closes the SSH app, your agents keep running; running herdr upon reconnection restores your exact workspace.
  • 3. Notification Plane (Bark / ntfy) — Timely Awareness: When an agent pauses on a permission prompt (blocked) or finishes a task (Stop), a local lifecycle hook fires a curl push notification straight to your phone’s lock screen—eliminating manual status polling.

6.3 Daily Usage Tutorial: Attaching, Approving Prompts, and Detaching Safely

Landing in the shell is just the entry point; your daily mobile workflow revolves around the persistent session layer:

  1. Re-attach to Your Live Workspace in One Command:
    Type herdr and press Enter. All project workspaces, agent panes, and sidebar status indicators appear immediately.
  2. Switching Panes and Approving Agent Permission Prompts on Mobile:
    • Touch Selection: Termius natively forwards terminal mouse events. Tap directly on any split pane to focus it, or tap a red blocked item in the herdr sidebar to jump straight to the agent awaiting confirmation.
    • Approving Tool Calls: Use the ↑ ↓ arrow keys and Enter on the Termius extended keyboard bar above the virtual keyboard to approve Claude Code / OpenCode permission prompts, or use mobile voice dictation to send follow-up instructions.
    • Viewport Adjustment: Rotate your phone to landscape mode when viewing side-by-side panes, and pinch-to-zoom to adjust font size on the fly.
  3. Clean Detach and Drop-Safe Recovery:
    • Clean Detach: Tap CTRL on the Termius accessory bar (it highlights to lock) → tap b (sends prefix Ctrl+b) → tap q (herdr detach key). You return to the outer shell while all panes keep running in the background.
    • Zero-Loss on Hard Disconnects: Even if you swipe Termius closed or lose cellular signal on a train without detaching, nothing is lost—the Mac-side herdr server daemon owns the PTYs. Reconnect and type herdr to resume right where you left off.

9. Field Notes: Three Troubleshooting Traps That Cost an Afternoon

The entire setup takes 30 minutes to configure, yet I spent hours debugging three deceptive failure modes. Every single one reinforces the same engineering rule: when troubleshooting hits a wall, question your measurement tools first.

9.1 Trap 1: Local Port Probes Returning 100% False Positives

  • Misleading Symptom: Running nc -zv <VPS_IP> 6022 from the Mac always returned succeeded! instantaneously—even when frps was stopped—yet actual SSH connections hung and timed out.
  • Root Cause: A proxy client running in TUN mode (Clash / mihomo) was active on the Mac. Its virtual network interface intercepted all outbound TCP SYN packets via fake-ip and completed the TCP handshake locally inside the TUN stack. nc was reporting a local proxy ACK, while zero packets actually left the machine.
  • Takeaway: Never trust port probes (nc, telnet) run from a host with an active TUN proxy. Always verify external reachability from an independent cloud host or a phone on cellular data.

9.2 Trap 2: Silent sshd Timeouts on the VPS Loopback Path

  • Misleading Symptom: To test the tunnel quickly, I ran ssh -p 6022 user@127.0.0.1 directly on the VPS. TCP connected and frp logs showed the proxy forwarding cleanly, but the SSH handshake hung for 4 seconds and died without receiving a single byte of the SSH-2.0-OpenSSH banner—even though nc 127.0.0.1 22 on the Mac returned the banner instantly.
  • Debugging Detour: I ruled out frp version mismatches, TLS settings, work connection pools, and macOS sshd PerSourcePenalties / MaxStartups. I even attached a Python echo server to the exact same tunnel—the echo server responded instantly, while only sshd stayed silent.
  • Root Cause: This was an artifact specific to the VPS self-loopback path (127.0.0.1:6022). The moment I tested from a separate cloud host over the public internet (External Host → VPS Public IP:6022 → Tunnel → Mac sshd), the SSH banner appeared in milliseconds on the first try. I had wasted hours debugging a synthetic loopback path that no real client ever takes.
  • Takeaway: Always test along the exact network path your real client uses.

9.3 Trap 3: The Cloud Security Group Blindspot

  • Misleading Symptom: I picked an arbitrary entry port in frps.toml, verified via ss -tlnp on the VPS that frps was listening, saw start proxy success in frpc.log, and assumed the port was reachable—until an external probe revealed silent packet drops.
  • Root Cause: Cloud Security Groups enforce filtering at the hypervisor boundary outside the guest OS kernel; neither ss nor iptables can see them. Inspect your cloud console’s allowed port ranges before choosing allowPorts and remotePort.

(Bonus macOS note: macOS does not ship with the GNU timeout binary. Writing timeout 5 ssh ... in scripts fails silently; use SSH’s native -o ConnectTimeout=5 flag or install coreutils via Homebrew for gtimeout.)

10. Production Readiness & Security Checklist

Run through these 6 checks in order before calling the deployment production-ready:

  1. VPS Listener Check: ss -tlnp | grep -E '7000|6022' shows both ports in LISTEN state.
  2. Mac Tunnel Check: tail ~/.config/frp/frpc.log shows login to server success and [mac-ssh] start proxy success.
  3. Reboot Self-Heal Check: Reboot the Mac once and verify frpc reconnects automatically via LaunchAgent without manual login.
  4. Mobile Takeover Loop: Put your phone on cellular data → connect via Termius → run herdr → send a message to a live agent and confirm it responds.
  5. Cross-Device Continuity: Detach on mobile (Ctrl+b q), then run herdr on the Mac desktop terminal and verify the session state is intact.
  6. Password Surface Rejection: Run ssh -o PubkeyAuthentication=no -p 6022 <user>@<VPS_IP> true from an external host and confirm Permission denied (publickey).

11. Next-Level Evolution

  • Second Control Surface (Laptop / iPad): Add a 4-line host alias to ~/.ssh/config on any secondary laptop to connect through the same tunnel. If you use herdr, run herdr --remote <ssh-alias> to turn your local terminal into a native thin client attached to the remote Mac’s herdr server.
  • Zero Public Port Exposure (WireGuard / STCP): To hide port 6022 from internet scanners entirely, use frp stcp (Secret TCP) mode for laptop-to-Mac access, or run a lightweight WireGuard hub on the VPS so both your phone and Mac communicate over an encrypted private mesh.
